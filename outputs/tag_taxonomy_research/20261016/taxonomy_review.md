## 「失敗」と実行状態の設計

次の情報を別のフィールドとして持つ。

- パターンについての記述：成立、失敗、未確定、判定不能。出典の表現と、対象となるパターンを添える。
- 執行についての振り返り：飛び乗り、早すぎた等。取引損益やパターン成立から推測しない。
- 売買の損益：実口座、Paper、DEMO、仮定のそれぞれの台帳。通貨、実現／未実現、照合状況も保持する。
- 口座環境：実口座、Paper、DEMO、未確認。
- 行動：約定、注文のみ、未約定、取消、未発注、未確認。複数の行動がある場合はイベントごとに保持する。
- 記録の性質：実況、観察、未実行候補、本人振り返り、後日仮説等。本人振り返りと実取引は同時に存在し得る。

「ロールリバーサル失敗」と明記されても、対象が特定できなければ「原文に失敗表記あり／対象未特定」とする。損失だったことだけを根拠に、パターン失敗を付けない。

06-05 6976の「失敗からSELL IN候補」では、観察したロールリバーサルの失敗と、その後に検討したSELL候補を区別する。未実行のSELL候補自体に失敗結果を付けない。

10-15 5803はPaper約定の記録として扱う。4回の買いは1場面に関連する売買イベントとして保持し、「4場面」と数えない。Paperの−10,800円は実口座集計へ入れない。

10-14 6857には本人の未実行候補の振り返りと、Paper指値の未約定・取消の情報がある。場面の単一ステータスを上書きする代わりに、関連する注文イベントと候補の記録を別に持つ。実約定という語だけで口座が実口座だと推定しない。

## 辞書と場面注釈の構造

既存のtagキー、scene id、case_idを参照する追加レイヤーを推奨する。原文表記と旧レコードを保持したまま、検索の解釈を追加できる構造とする。

| レイヤー | 必要な情報 |
|---|---|
| タグ辞書 | 既存tagキー、表示名、定義、定義の状態、確定した別名、定義書へのリンク |
| タグ関係 | 関係元・関係先、種類（別名／親子／関連／複合表記の分解）、状態（本人確定／現行辞書登録／提案／保留）、根拠 |
| 場面への注釈 | 既存scene/case参照、元表記、基本概念、基準・後続状態等の属性、出典、判定の状態 |
| 実行イベント | 場面参照、口座環境、行動、時刻、実約定情報、損益の出典と確認状況 |
| 場面間の関係 | 主場面・環境観察場面の参照、関係の根拠、対象期間、時刻照合状況 |

タグ関係ごと、場面属性ごとに出典を持たせる。一つの場面の「高確度」を、時間足や損益など全フィールドの確認済みに転用しない。確認の状態と、解釈の確信度も別にする。

下記は追加レイヤーの構造例であり、現行データへの登録指示ではない。

```json
{
  "scene_ref": "2026-10-15:5803:countertrend-long-stop",
  "raw_terms": ["ロールリバーサル失敗"],
  "annotations": [
    {
      "field": "setup.family",
      "value": "ロールリバーサル",
      "basis": "複合表記の分解案",
      "status": "提案"
    },
    {
      "field": "pattern_outcome.reported_label",
      "value": "失敗",
      "target": null,
      "status": "原文に表記あり・判定対象は未確認"
    }
  ]
}
```

実装時は注釈ごとに直接出典と該当見出しを追加する。原文タグは削除せず、分解結果が提案段階なら初期検索の自動一致に使用しない。既存case_idとscene idが両方ある場合は両方を保持し、同じ場面だと確認できる対応だけを登録する。

## フィルターの既定動作

1. タグを一つ選ぶと、正規名と確定別名を一つの検索グループとして扱う。文字列の部分一致による類似タグの自動統合はしない。
2. 複数タグは初期設定をANDにし、「すべてを含む／いずれかを含む」を切り替えられるようにする。一つの検索グループ内では別名や許可された展開先をORで評価する。
3. タグ、主対象の銘柄、実行状態、時間足等は同じ場面に対して評価する。銘柄候補一覧も、タグに一致した場面から作る。
4. 「複合表記を含める」は任意とし、レビュー済みの分解だけを適用する。一致理由を「元タグ一致／確定別名／複合表記から一致」と表示する。
5. 関連タグは「関連候補」として件数付きで案内し、選択したときに検索条件へ追加する。初期結果には混ぜない。親子展開も採用済みの関係に限る。
6. フリーテキスト検索の本文一致と、意味を指定するタグフィルターを区別する。本文に別銘柄や否定文があることだけでタグ付与しない。
7. 日誌一覧は一致した場面からまとめる。タグ未分類の日誌は台帳入口に残し、タグ未分類＝取引なしとしない。

条件式は次の意味にする。

```text
一致する場面 = tag_condition(scene)
             AND primary_instrument_condition(scene)
             AND execution_condition(scene)
             AND other_facet_conditions(scene)

一致する日誌 = 一致する場面のdiary参照を重複除去した集合
```

同じ日誌にタグと銘柄がそれぞれ登場するだけでは一致させない。

|---|---|
| ロールリバーサル＋285A | 10-14の285A場面は本人確定別名で一致。同日の6857場面の銘柄条件を流用しない |
| ロールリバーサル＋5803 | 「失敗」を文字列の前方一致で自動追加しない。分解が採用され、複合表記を含めた場合に10-15のPaper場面を扱う |
| BB COMP＋JP225 | 08-12確認済み事例と10-15の明示BBコンプを対象にできる。09-09等のID未対応の証拠行は、場面対応が確認されるまで証拠台帳に残す |
| BB COMP＋7974 | 06-30のレンジ収縮だけを根拠に一致させない |
| BB COMP＋後続状態=下降継続 | 10-15の本人分類を使える。下方ブレイクの確認時刻や売り実行まで推定しない |
| タグ＋不明銘柄 | 不明銘柄専用の絞り込みで表示。具体的な銘柄の結果には含めない |

## JP225の観察と個別銘柄の結び付け

場面の主対象と環境参照を区別する。JP225のBB COMP観察場面はJP225を主対象とする。5803の取引にJP225の環境を参照する記述があっても、5803にBB COMPが発生したというタグには変換しない。

「BB COMPの日に5803がどう動いたか」を探すための入口は、明示的な場面間リンクを使う。リンクの根拠となる日誌記述と、観察対象の期間・取引時刻との対応を保存する。同日という理由だけで環境の因果関係や同時性を登録しない。「同日の日誌も見る」は日付ベースの補助検索として別に表示できる。

指数、先物、CFD、ETF、チャート提供元の価格系列は同一視しない。OANDA等の提供元が既知なら保持し、JP225という表示名だけで全チャートの価格基準を補わない。

## BB COMPの記録項目と未知値

次の項目を記録欄として必須化する。ただし値は「不明／未記載／未照合」を許容する。不明値があっても、本人確認済みの事例や明示的な原文タグを索引から落とさない。

| 項目 | 記録する内容 |
|---|---|
| 対象 | 銘柄・商品種別・価格系列・提供元 |
| 足 | 時間足、通常足等の足種、タイムゾーン |
| 指標設定 | 期間、中心線の種類、標準偏差倍率、入力価格系列 |
| 幅 | 原文値、単位、概数か、上下バンド差か等の測定方法 |
| 測定時点 | 観察時刻と対象バー、確定足か未確定足か |
| 収縮の判断 | 本人ラベル、比較対象期間、比較方法とその出典 |
| 後続状態 | 方向、ブレイク等のイベント、判断期間、本人の分類か検証値か |
| 出典 | 元資料、見出し・位置、短い引用、確認状況 |

599と641等の複数値は、対応する時刻・設定が分かるまで一つの計測区間や最小値・最大値に変換しない。「599〜641」という原文要約と未照合の状態を保持する。10-14の約850円は「BBコンプレッションとしてはまだ幅が大きい」という境界・否定の文脈として扱い、BB COMP成立例へ自動追加しない。

数値フィルターは、必要な計測条件が確認できる事例に適用する。除外された未知値の件数を表示し、「不明も表示」で別枠に出せるようにする。概数の600円を厳密なしきい値判定の600円と同じ精度で扱わない。時間足・設定・計算方法・単位・価格系列が違う記録を、同条件の幅比較やイベント後成績の計算へ投入しない。

## タグ別の定義・取り組み方ひな型

各項目に「本人確定／出典に明記／設計上の提案／未確定」を付ける。検索上の定義と売買ルールの確定状況を別に表示する。

```text
タグ名・既存tagキー：
定義書の版・更新日：
検索グループの状態：
成立条件・売買ルールの状態：

1. 何を探すタグか（短い定義）
2. 確定別名、複合表記、関連タグ、親子関係
3. 含める記録／除外する記録（否定・先行サイン・類似形も区別）
4. 観察対象：銘柄、価格帯・指標、足、時刻、計測方法
5. 観察時に記録する順番と、成立・無効・判定不能の記録欄
6. 本人の実行条件・見送り条件・撤退条件
   各条件に出典。未確定なら空欄＋未確定の理由
7. 口座環境、行動、本人振り返り、後日仮説の記録方法
8. パターンの結果、執行評価、実損益／Paper等の扱い
9. 根拠scene/case IDと直接出典、境界例・不一致例
10. 未決事項、更新履歴、本人が確定した日付と対象範囲
```

現段階の「取り組み方」には、確認する項目と記録手順を書ける。本人の条件がないENTRY・LC・TPや、未検証の勝ちやすさは記入しない。

## 件数と集計の扱い

- 日誌数は日誌ID、日付数は日付、場面数は確認済みのscene/case対応、銘柄数は主対象コードでそれぞれ数える。日付だけを日誌IDに代用しない。
- 元表記数、正規タグ数、提案中の正規化ラベル数を別に表示する。確定別名が複数一致しても、正規タグの件数や場面数を増やさない。
- 同じ場面が基本タグと複合表記の両方で一致しても1場面。関連一致は直接一致と分けて表示する。
- 注文数、約定明細数、取引数、場面数を区別する。複数イベントがある場面の口座別件数は重複し得るので、内訳の単純合計を総場面数としない。
- 損益は口座環境・通貨・実現区分・照合状況ごとに集計し、source_conflict等の保留値の件数も表示する。未知値は0として計算しない。
- 今回のCSVは24証拠行であり、確定した24固有sceneとは数えない。scene/case ID付きは12行。13種類の正規化候補ラベルも、そのまま13個の確定正規タグとはしない。

## 証拠レビューで見つかった修正・注意点

### 08-10 7012は別日抜粋の混入として扱う

08-10日誌（ローカル出典パスは公開版から省略）には、08-10の7012実取引と+1,300円の記載がある。一方、同ファイルの別見出し（ローカル出典パスは公開版から省略）は「金曜日（8月7日）の指標トレード検証」であり、「8月7日の注文CSVには7012の約定はありません」はその節の記述である。

元レポートとCSVは調査時点の記録として残し、本書を訂正注記とする。後続処理で、元レポートの「実行状態の矛盾」を未検討のまま再利用しない。

### 03-11 7974の証拠1行は取引2件に言及する

03-11日誌（ローカル出典パスは公開版から省略）には09:49と09:51の別取引があり、本文は共通のロールリバーサル文脈で説明している。CSVは両方を一つの根拠行に引用している。場面と取引の対応が確認されるまでは、1場面とも2場面とも自動的に決めない。取引は別に保持し、同じパターン場面を共有するかを確認する。

## 実装へ渡す順序と確認例

1. 既存ID・タグ原表記・出典を保持した状態で、関係と場面注釈の追加データを準備する。提案を本人確定として登録しない。
2. 確定別名の検索、同一場面AND、銘柄候補の連動、不明の表示を先に整える。場面ID未対応の証拠は台帳へ残す。
3. レビュー済み複合表記の分解を追加し、初期検索と展開検索の結果・一致理由を比較できるようにする。
4. 定義書の検索範囲と売買条件の状態を別に表示し、場面カードから元表記・直接出典へ移動できるようにする。
5. 08-10の別日抜粋等を根拠フィールド単位で点検する。修正履歴を持ち、別日節の銘柄・注文状態を場面へ持ち込まない。

実装後に確認する具体例は、10-14の285A/6857の交差誤一致がないこと、10-15の5803がPaperとして出ること、未実行候補の損益が実口座へ入らないこと、RR失敗が部分一致だけで混入しないこと、06-30 7974がBB COMPへ混入しないこと、BB設定不明でも本人確認例が検索できること、未知値が0にならないこと、別名・複合表記の重複で場面数が増えないことである。

本人への追加確認が必要なのは、実際の成立・失敗の判定条件、VWAP等が必須か任意か、売買の実行・見送り・撤退条件、BBの計測条件と比較方法である。未回答の項目は未確定のまま記録でき、上記の分類・検索設計を妨げない。
